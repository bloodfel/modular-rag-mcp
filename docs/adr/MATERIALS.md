## ADR-0001 重排方案选型：none / bge / Jev / LLM

**决策问题**：检索加第二段排序时用哪个方案。
**备选项**：① 不重排 ② 本地 cross-encoder（`BAAI/bge-reranker-base`）③ 云端 Jev API ④ LLM 重排。

**实测数据**（来源：`reports/rerank_benchmark_2026-09-22.md`；BEIR test split 固定抽样 50 query/数据集，seed=42，depth=10）：

| 维度 | none | bge | jev | llm |
|---|---|---|---|---|
| nDCG@10 ×100（scifact/bm25） | 64.99 | 65.27 | **73.29** | 66.16 |
| 增益（相对 none） | — | +0.3 | **+8.3（相对 +12.8%）** | +1.2 |
| p50 / p95 延迟 | 0 | 0.6s / 0.6s | 1.4–2.1s / **1.9–5.1s** | 37–45s / 43–55s |
| 成本 / 千次查询 | $0 | $0（本地） | **$0.13–0.18** | token 不可见 |
| 失败回退次数 | 0 | 0 | 0 | 0 |

**建议结论**：默认推荐 **Jev**——质量收益最大且成本可忽略，失败自动回退原序；离线/无外网场景退到 bge；LLM 重排仅作离线实验（延迟差两个数量级）。生产默认 `rerank.enabled=false`，是按需开启的可选增强（不外呼、不烧钱）。
**可引用句式**：+8.3 nDCG@10（相对 +12.8%）、$0.17/千次查询、p95 < 5.1s。

## ADR-0002 混合检索融合：RRF（k=60）

**决策问题**：dense 与 sparse 两路结果如何合并成一份排序。
**备选项**：① 只用单路 ② 加权分数求和 ③ RRF 排名融合。

**实测数据**（同基准报告，none 重排列）：

| 数据集 | bm25 | dense | hybrid |
|---|---|---|---|
| nfcorpus nDCG@10 | 35.98 | 36.94 | **38.22** |
| scifact nDCG@10 | 64.99 | 67.90 | 67.40 |

**建议结论**：采用 **RRF（k=60，业界默认）**。核心理由：dense 余弦相似度与 BM25 分数**量纲不可比**，加权求和必须先解决归一化和权重调参；RRF 只用排名，无监督、无需调参、对任一路退化天然鲁棒。nfcorpus 上 hybrid 稳定优于单路；scifact 上与 dense 持平——融合不保证每格都赢，但把"选错单路"的风险消掉了。
**可引用句式**：nfcorpus +2.8 nDCG（hybrid 对 dense）；k=60 无参融合。

## ADR-0003 本地 bge 强制串行：torch MPS 原生段错误

**决策问题**：查询级线程并发下，本地 cross-encoder 能否并发推理。
**背景事实**：torch 2.14 + Apple Silicon MPS 后端，并发提交推理触发**原生段错误**（exit 133/139）——不是 Python 异常，`try/except` 捕获不到，进程直接死，整个跑批报废。

**决定**：本地 bge 推理**强制串行**；远端 API（Jev / LLM）保留查询级并发（默认 6 workers）。两者在同一跑批里共存。
**后果**：修复后 12 个 cell 全量跑完、失败回退 0；代价是本地模型无法并发提速（p95 仍 < 0.7s，可接受）。
**可引用句式**：MPS 并发=进程级崩溃，只能靠架构隔离（串行锁）而非异常处理。

## ADR-0004 MCP 传输：stdio 默认 + stateless Streamable HTTP

**决策问题**：MCP Server 用哪种传输方式。
**备选项**：① 仅 stdio ② SSE ③ Streamable HTTP（stateful）④ Streamable HTTP（stateless + JSON 响应）。

**实测/事实依据**（来源：`DEV_SPEC.md` 3.2.2）：选定双模式——stdio 默认（本地 IDE 零配置、数据不出本机，stdout 只走 MCP 消息、日志全走 stderr）；`--http` 用官方 SDK 的 `StreamableHTTPSessionManager`（stateless + JSON 模式，Starlette/uvicorn）。
**理由**：检索是只读请求-响应，**没有会话状态可存**——stateless 免 session 管理、天然可横向扩展、无会话泄漏面；JSON 响应模式对 curl/脚本调试友好；stdio 保留给本地 Agent 集成。
**后果（已知边界）**：面向公网需自行叠加反向代理 + 鉴权（当前未内置）。这条要在 ADR 里明确写"不做什么"。

## ADR-0005 Jev min_score 阈值：4.0 / 1.0 / 不限

**决策问题**：Jev 重排分数过滤阈值取多少。现状是**两处不一致**：生产默认 4.0（`src/core/settings.py`、`jev_reranker.py`），基准脚本用 1.0（纯排序口径）——本 ADR 就是把它定下来。

**备选项**：① 4.0（严格，低相关直接滤掉）② 1.0（宽松）③ 不过滤。

**实测数据**（`reports/min_score_{4.0,1.0,0}/`，BEIR test split 50 query，hybrid 检索，仅 jev 重排）：

| min_score | scifact nDCG@10 | nfcorpus nDCG@10 | MRR（scifact） | Hit@10（scifact） | **空结果率** | 均存活候选 | 成本/千次 |
|---|---|---|---|---|---|---|---|
| **4.0（生产默认）** | 61.51 | 31.49 | 63.0 | 66 | **24%** | 1.2–2.7 | $0.13 |
| 1.0（基准脚本） | 70.28 | 38.32 | 68.6 | 80 | 0–2% | 6.8–7.0 | $0.16–0.17 |
| 0（不过滤） | **72.05** | **38.43** | 71.0 | 80 | 0% | 10.0 | $0.17–0.18 |

**建议结论**：**默认改为 1.0**（或 0）。4.0 的代价被严重低估——每 4 条 query 就有 1 条返回空结果（候选全被滤掉），同时丢 ~9 个 nDCG 点；省下的成本只有 $0.04/千次。若确实要用高阈值做"质量门"，必须配套"全滤空时回退到未重排 top-k"的兜底逻辑，否则前端会直接无结果。
**可引用句式**：阈值 4.0→1.0 换回 +8.8 nDCG@10，代价 $0.04/千次；24% 空结果率是拍脑袋阈值的实测代价。
